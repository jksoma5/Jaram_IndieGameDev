# AI와 Unity로 시작하는 인디게임 개발 — 발표 기획안

> 대상: 신입생 (프로그래밍·Unity 경험 거의 없음 가정)
> 목표: "AI로 게임을 만들 수 있다"는 감각 → "프로젝트로 끝까지 완성·배포할 수 있다"는 계획 능력 → "직접 에디터에서 AI와 함께 개발한다"는 실습 능력

---

## 0. 전체 흐름 한눈에 보기

| 순서 | 파트 | 핵심 질문 | 형태 | 권장 시간 |
|---|---|---|---|---|
| 1 | 좋은 사례 소개 | "AI로 이런 게 진짜 돼?" | 발표 | 15분 |
| 2 | AI 개발 방법의 이해 (원리 · 도구 · CLI · MCP) | "AI는 어떻게 코드를 짜고 에디터를 만지지?" | 발표 + 짧은 시연 | 30분 |
| 3 | AI로 간단한 게임 라이브 개발 | "얼마나 빨리, 얼마나 잘 돼?" | 라이브 데모 | 25분 |
| 4 | AI 개발 가능 범위 정리 | "어디까지 맡기고 어디부터 내가?" | 발표 + 토론 | 15분 |
| 5 | 배포 (Windows / Mac / 콘솔 / 웹) | "만들면 어디에 낼 수 있지?" | 발표 | 20분 |
| 6 | 프로젝트 매니징 (AI 활용 일정 계획) | "목표 기능까지 어떻게 일정을 짜지?" | 발표 + 워크시트 | 25분 |
| 7 | GitHub Desktop 버전관리 | "AI가 망쳐도 되돌릴 수 있게" | 발표 + 실습 | 25분 |
| 8 | Unity 프로젝트 생성 & 실행 | "내 손으로 Play 버튼 누르기" | 실습 | 30분 |
| 9 | 에디터에 MCP 연결 후 개발 | "AI가 에디터를 직접 만진다" | 데모 + 실습 | 40분 |
| 10 | 마무리 & 과제 | 다음 주까지 할 것 | 발표 | 5분 |

- 한 번에 진행하면 약 3시간 50분 (중간 휴식 2회 포함 시 약 4시간 10분).
- 여러 주로 나눌 경우 권장 분할:
  - **1주차**: 1~4 (동기 부여 + AI 원리·도구 + AI 감각) + 8 미리 설치 안내
  - **2주차**: 5~6 (배포 + 기획/일정) → 팀별 기획서 과제
  - **3주차**: 7~8 (GitHub Desktop + 프로젝트 생성·실행)
  - **4주차**: 9 (MCP 연결 개발) → 이후 팀 프로젝트 진행

> **순서를 이렇게 잡은 이유**
> "재미있다(1) → 어떻게 되는 건지 안다(2) → 할 수 있겠다(3~4)" 로 시작해서, AI의 한계를 알게 된 시점에 "그럼 계획이 필요하다(5~6)"로 넘어가고,
> 실제 개발 전 "되돌릴 수 있는 안전장치(7)"를 먼저 갖춘 뒤, 기본 조작을 이해한 사람만 "AI가 에디터를 직접 조작하는 단계(9)"로 들어간다.
> MCP는 **개념과 구조는 2에서 미리 설명**하고(라이브 데모를 이해하기 위해), **직접 연결하는 실습은 9에서** 한다. Unity의 기본 구조(씬, 게임오브젝트, 컴포넌트, Play 모드)를 모르면 AI가 무엇을 바꿨는지 판단할 수 없기 때문.

## 1. 좋은 사례 소개 (15분)

**목표**: "적은 인원·짧은 시간·AI 활용으로도 의미 있는 게임이 나온다"는 동기 부여.

### 슬라이드 구성
1. **오프닝 질문**: "게임 하나 만드는 데 몇 명, 몇 달이 필요할까?" (손들기 투표)
2. **1인/소규모 인디 성공 사례** — "작은 팀도 된다"
   - *Vampire Survivors*: 1인 개발로 시작, 단순한 조작 + 강한 코어 루프
   - *Balatro*: 1인 개발, 익숙한 규칙(포커)을 비틀어 성공
   - 메시지: **아이디어와 코어 루프가 핵심**, 그래픽·규모가 아니다
3. **AI 활용(바이브 코딩) 사례** — "AI로 이 속도가 된다"
   - Pieter Levels의 브라우저 비행 게임(fly.pieter.com): AI 코딩 도구로 짧은 기간에 제작·공개
   - Vibe Coding Game Jam(2025): 코드의 대부분을 AI로 작성하는 조건의 게임잼
   - (선택) 교내/동아리 선배 작품, 최근 게임잼 출품작 등 **가까운 사례**를 1개 넣으면 효과가 큼
4. **사례에서 뽑아낼 교훈 3가지**
   - 범위가 작다 / 코어 재미가 명확하다 / 빨리 공개하고 피드백을 받았다

### 준비물
- 각 사례 플레이 영상 15~30초 클립
- ⚠️ 매출·기간·이용자 수 등 **수치는 발표 직전 최신 자료로 재확인** 후 출처 표기

### 다음 파트로의 전환 멘트
> "이런 게임들을 AI로 어떻게 만드는 걸까요? 직접 만들어 보기 전에, AI가 코드를 짜는 원리와 도구부터 짚고 가겠습니다."

## 2. AI 개발 방법의 이해 — 원리 · 도구 · CLI · MCP (30분)

**목표**: 라이브 데모를 "마법"이 아니라 **"이해할 수 있는 과정"** 으로 보게 만들기.
AI가 어떻게 동작하는지, 어떤 도구 형태가 있는지, CLI 에이전트와 MCP가 무엇을 해주는지 큰 그림을 잡는다.

### 2-1. AI(LLM)는 어떻게 코드를 만드는가 (7분)
- **다음 단어(토큰) 예측기**: 앞의 글을 보고 "그다음에 올 가장 그럴듯한 조각"을 반복해서 이어 붙인다
  - 시연: 스마트폰 자동완성으로 문장 이어가기 → "이걸 엄청 크게 만든 게 LLM"
  - 코드도 글이다 → 수많은 코드를 학습했기 때문에 Unity C# 코드도 "그럴듯하게" 이어 쓴다
- **이 원리에서 나오는 4가지 특징** (수업 전체에서 계속 다시 등장)

| 특징 | 의미 | 개발할 때의 대처 |
|---|---|---|
| 학습 시점 이후를 모름 | 최신 Unity 버전 API를 틀리게 쓸 수 있음 | Unity 버전을 알려주고, 에러가 나면 원문을 그대로 전달 |
| 컨텍스트(작업 기억)가 한정됨 | 내 프로젝트를 **보여준 만큼만** 안다 | 관련 파일·에러·목표를 함께 제공, 작업 단위를 작게 |
| 확률적으로 답함 | 같은 질문에도 매번 다른 답 | 결과는 항상 Play로 검증 |
| 그럴듯한 오답(환각) | 없는 함수·설정을 자신 있게 말함 | "확실하지 않으면 모른다고 해줘", 공식 문서 확인 |

### 2-2. 챗봇에서 에이전트로 (5분)
- **챗봇**: 질문 → 답변 (텍스트만 주고받음, 실행은 사람이)
- **에이전트** = LLM + **도구(Tool)** + **반복 루프**
  - `목표 이해 → 계획 → 도구 사용(파일 읽기/쓰기, 명령 실행) → 결과 관찰 → 다시 계획 …`
  - 사람이 하던 "복사 → 붙여넣기 → 실행 → 에러 복사"를 AI가 스스로 반복
- 그림 1장: 사람이 중간에 있는 구조 vs AI가 직접 도는 루프

### 2-3. AI 개발 도구의 4가지 형태 (5분)

| 단계 | 형태 | 예시 | AI가 할 수 있는 일 | 사람이 하는 일 |
|---|---|---|---|---|
| ① | 웹 채팅 | Claude, ChatGPT, Gemini 웹 | 코드·설명 생성 | 복사·붙여넣기·실행·에러 전달 전부 |
| ② | IDE 통합 | VS Code + Copilot, Cursor | 열린 파일 기준 자동완성·수정 | 실행·검증 |
| ③ | **CLI 에이전트** | Claude Code, Codex CLI, Gemini CLI | 프로젝트 전체 파일 읽기·수정, 명령 실행 | 목표 제시·승인·검증 |
| ④ | **에이전트 + MCP** | CLI 에이전트 + Unity MCP | 위 + **Unity 에디터 직접 조작**(씬·오브젝트·콘솔) | 목표 제시·승인·검증 |

- 메시지: **아래로 갈수록 AI가 직접 하는 일이 늘고, 사람의 역할은 "지시와 검증"으로 이동**
- 수업 흐름과 연결: 8번에서는 ①로 수동 체험 → 9번에서 ③+④로 개발

### 2-4. CLI와 CLI 에이전트 (6분)
- **CLI(Command Line Interface)란?** 마우스 대신 명령어로 컴퓨터를 다루는 창(터미널)
  - 최소 명령만 소개: 현재 위치 확인, 폴더 이동(`cd`), 목록 보기(`ls` / `dir`)
  - "검은 화면"에 대한 두려움 낮추기가 목적, 깊게 다루지 않음
- **CLI 에이전트가 강력한 이유**
  - 프로젝트 폴더에서 실행 → 폴더 전체를 맥락으로 사용
  - 파일 생성·수정, 빌드·테스트 명령 실행을 직접 수행
- **사용 흐름 (Claude Code 예시로 시연)**
  1. 터미널에서 Unity 프로젝트 폴더로 이동 → `claude` 실행
  2. 프로젝트 규칙 파일(예: `CLAUDE.md`)에 "Unity 6, URP 2D, C# 스크립트는 Assets/Scripts에" 같은 규칙 기록 → 매번 설명할 필요 없음
  3. 요청 → AI가 계획 제시 → 파일 변경마다 **승인/거절** (권한 모드 설명)
  4. 변경 결과를 GitHub Desktop에서 확인 (7번과 연결 예고)
- **좋은 요청(프롬프트) 공식**
  - `목표` + `맥락(관련 파일·Unity 버전)` + `제약(건드리지 말 것)` + `완료 기준(어떻게 확인할지)`
  - 나쁜 예: "게임 만들어줘" / 좋은 예: "PlayerController.cs에 스페이스바 점프를 추가해줘. 바닥에 닿아 있을 때만 점프 가능. 다른 스크립트는 수정하지 마."
  - 큰 작업은 "먼저 계획만 세워줘" → 확인 후 실행

### 2-5. MCP — AI에게 Unity 에디터를 쥐여주는 방법 (7분)
- **문제**: CLI 에이전트는 파일은 만질 수 있지만, **Unity 에디터 안의 상태**(씬 구성, 컴포넌트 값, 콘솔 에러, Play 모드)는 직접 보거나 조작하지 못한다
- **MCP(Model Context Protocol)**: AI와 외부 프로그램을 연결하는 **표준 규격**
  - 비유: **USB 규격** — 규격만 맞으면 어떤 AI(클라이언트)든 어떤 프로그램(서버)이든 꽂아서 쓴다
- **구조 그림**
  ```
  [AI 클라이언트]  ⇄  [MCP 서버]  ⇄  [Unity 에디터 패키지]
   Claude Code 등     "도구 목록" 제공     실제로 씬·오브젝트·콘솔을 조작
  ```
  - MCP 서버가 AI에게 "나는 이런 도구가 있어"를 알려줌
    예: `오브젝트 생성`, `컴포넌트 추가`, `스크립트 작성`, `콘솔 로그 읽기`, `Play 모드 실행`
  - AI는 목표를 위해 필요한 도구를 골라 호출 → 결과를 보고 다음 행동 결정 (2-2의 에이전트 루프)
- **설정은 크게 2단계** (원리만 보여주고, 실제 설치는 9번에서)
  1. **Unity 쪽**: Package Manager로 MCP 지원 패키지 설치 → 에디터 안에서 연결 대기
  2. **AI 클라이언트 쪽**: MCP 서버 등록
     - CLI 명령으로 등록하는 방식 (예: Claude Code의 `claude mcp add ...`)
     - 또는 설정 파일(JSON)에 서버 정보를 적는 방식
     ```json
     {
       "mcpServers": {
         "unity": { "command": "<MCP 서버 실행 명령>", "args": ["<옵션>"] }
       }
     }
     ```
  3. 확인: AI에게 "현재 씬의 Hierarchy를 알려줘" → 실제 씬 내용이 나오면 성공
- **선택지**: Unity 공식 AI/MCP 지원 패키지, 오픈소스 커뮤니티 Unity MCP 패키지
  - ⚠️ 패키지명·설치 명령·지원 버전이 빠르게 바뀌므로 **슬라이드에는 구조만**, 정확한 명령은 수업 직전 확인한 설치 가이드로 배포
- **주의점**: MCP는 AI에게 "손"을 주는 것 → 권한 승인, 작업 전 커밋, 결과 검증이 더 중요해진다

### 전환 멘트
> "이제 AI가 어떻게 생각하고, 어떤 도구로 손을 뻗는지 알았습니다. 이 도구들로 실제로 게임을 만들어 보겠습니다."

## 3. AI로 간단한 게임 라이브 개발 (25분)

**목표**: 짧은 시간에 "그럴듯한" 게임이 만들어지는 과정을 눈으로 보여주기.

### 데모 설계
- **게임 선정 기준**: 규칙이 한 문장으로 설명되는 것
  - 예: "떨어지는 장애물을 피하며 오래 버티기", "벽돌깨기", "탑다운 생존 슈터(뱀서라이크 축소판)"
- **진행 방식** (단계별로 프롬프트를 화면에 크게 보여줌)
  1. 기획 프롬프트: "이런 게임을 Unity로 만들고 싶어. 필요한 오브젝트와 스크립트 목록을 정리해줘"
  2. 핵심 기능 구현: 플레이어 이동 → 적/장애물 생성 → 충돌·게임오버
  3. 퀄리티 업: 점수 UI, 화면 흔들림, 파티클, 사운드, 난이도 상승 곡선
  4. 플레이 → 버그 발견 → 에러 메시지를 AI에 그대로 전달 → 수정 (**일부러 보여줄 것**)
- **"퀄리티가 높아 보이는" 포인트를 명시적으로 설명**
  - 게임 필(Game Feel): 타격감, 이징, 화면 흔들림, 사운드 피드백
  - 일관된 색감/폰트 하나만 지켜도 완성도가 크게 올라간다

### 리스크 대비
- 라이브 데모 실패 대비 **단계별 완성본 브랜치(또는 커밋)를 미리 준비**하고, 막히면 다음 단계로 점프
- 녹화본 백업
- 사용 AI 도구·요금제·인터넷 연결 사전 점검

### 2번 내용과 연결하며 진행
- 지금 쓰는 도구가 2-3 표의 어느 단계(① 채팅 / ③ CLI 에이전트 / ④ MCP)인지 화면 구석에 표시
- AI가 도구를 호출할 때마다(파일 생성, 콘솔 읽기 등) "방금 2-2의 에이전트 루프가 한 바퀴 돌았다"고 짚어주기
- 목적은 "결과물"을 보여주는 것. 수강생이 직접 연결하는 실습은 9번에서 한다.

## 4. AI가 어느 정도까지 개발할 수 있는가 (15분)

**목표**: 데모에서 본 것을 근거로 AI의 **잘하는 일 / 못하는 일**을 정리 → 계획의 필요성으로 연결.

### 슬라이드: 역할 분담 표

| AI가 잘하는 것 | 사람이 반드시 해야 하는 것 |
|---|---|
| 정형화된 기능 코드 (이동, 점프, 스폰, UI 갱신) | "무엇이 재미있는가" 결정 (기획·밸런스) |
| 에러 메시지 해석, 버그 원인 추정 | 플레이테스트와 감각적 판단 |
| 반복 작업 (오브젝트 배치, 설정값 일괄 변경) | 전체 구조 설계, 범위(Scope) 결정 |
| 문서·튜토리얼 요약, 개념 설명 | 결과물 검증 (AI 말을 그대로 믿지 않기) |
| 프로토타입 빠르게 뽑기 | 아트 방향성, 저작권·라이선스 판단 |

### 강조할 한계
- **규모가 커질수록 급격히 어려워진다**: 파일·시스템이 많아지면 AI가 맥락을 놓침 → 작은 단위로 쪼개야 함
- **"돌아가는 것"과 "완성된 것"은 다르다**: 마지막 20%(폴리싱, 버그, 빌드, 배포)가 시간의 대부분
- **에셋(그림·사운드)** 은 별도 문제: 생성형 AI 에셋은 각 플랫폼의 AI 콘텐츠 정책(예: Steam의 AI 사용 고지)을 확인해야 함
- **책임은 개발자에게**: AI가 쓴 코드도 내가 이해하고 설명할 수 있어야 함

### 미니 토론 (5분)
- "방금 데모 게임을 Steam에 출시하려면 무엇이 더 필요할까?" → 자연스럽게 5·6번(배포·일정)으로 연결

## 5. 배포 — 어디에, 어떻게 낼 수 있나 (20분)

**목표**: "완성"의 기준을 **배포 가능한 빌드**로 잡게 하고, 플랫폼별 진입 장벽을 이해시키기.

### 5-1. 배포 파이프라인 개요
`개발 → 빌드(Build Profiles) → 테스트 → 스토어 페이지 준비 → 심사/등록 → 출시 → 업데이트`

### 5-2. 플랫폼별 정리

| 플랫폼 | 대표 스토어 | 진입 장벽 | 신입생 현실 난이도 |
|---|---|---|---|
| **웹** | itch.io (WebGL), 학교/개인 페이지 | 거의 없음 | ★☆☆☆ — **첫 배포로 강력 추천** |
| **Windows** | itch.io, Steam, Epic Games Store, Microsoft Store | Steam: 앱당 등록비(Steam Direct), 스토어 페이지 사전 공개 기간 등 | ★★☆☆ |
| **macOS** | Steam, itch.io, Mac App Store | Apple 개발자 프로그램(연회비), 코드 서명·공증(Notarization) 필요, 빌드·서명에 Mac 필요한 경우 많음 | ★★★☆ |
| **콘솔** (Switch / PlayStation / Xbox) | 각 플랫폼 스토어 | 플랫폼사 개발자 등록·승인, 전용 개발 키트, 사업자 요건, 인증 심사(TRC/Lotcheck 등), Unity 콘솔 빌드 모듈은 승인 후 제공 | ★★★★ — **퍼블리셔 협업 또는 인디 프로그램(예: ID@Xbox) 경로** |

### 5-3. 꼭 알려줄 체크리스트
- **스토어 페이지는 "마케팅 도구"**: 캡슐 이미지, 트레일러, 스크린샷, 짧은 소개문 → 개발 중반부터 준비
- **위시리스트**: Steam은 출시 전 위시리스트 수가 초기 노출에 중요
- **등급 분류**: 국내 출시 시 게임물 등급분류 필요 여부(자체등급분류 사업자 경유 여부 포함) 확인
- **AI 콘텐츠 고지**: Steam 등은 AI 생성 콘텐츠 사용 시 신고/고지 항목이 있음
- ⚠️ 등록비·수수료·연회비·대기 기간 등 **수치는 발표 직전 각 공식 문서에서 재확인** 후 표기

### 5-4. 수업에서의 배포 목표 제안
- 1차 목표: **itch.io 웹(WebGL) 또는 Windows 빌드 공개** (전원 달성)
- 2차 목표(희망 팀): Steam 스토어 페이지 개설 / 게임잼 출품
- 콘솔은 "구조와 경로를 아는 것"까지만

## 6. 프로젝트 매니징 — AI 툴을 쓰는 프로젝트의 일정 계획 (25분)

**목표**: 목표 기능(Feature) → 작업(Task) → 일정(Milestone)으로 쪼개는 법을 익히고, **AI 사용을 전제로 한 현실적인 일정**을 세우게 하기.

### 6-1. 범위 정하기: MVP와 코어 루프
- **코어 루프 한 줄 정의**: "____ 해서 ____ 를 얻고, 그걸로 ____ 한다"
- 기능을 3단계로 분류
  - **Must** (없으면 게임이 아님) / **Should** (있으면 좋음) / **Could** (시간 남으면)
- 원칙: **Must만으로 플레이 가능한 빌드를 일정의 30~40% 시점에 확보**

### 6-2. AI 시대의 일정 추정법
- AI는 **"코드 작성" 시간**을 크게 줄이지만, 아래 시간은 줄이지 못한다
  - 기획 결정, 플레이테스트, 통합 시 발생하는 버그, 에셋 제작, 빌드·배포 이슈
- 추정 방법 제안
  1. 기능별로 "AI에게 시킬 프롬프트 단위"로 쪼갠다 (한 번에 하나의 시스템)
  2. 각 작업에 **구현 시간 + 검증 시간**을 따로 적는다 (검증 ≥ 구현인 경우가 많음)
  3. 전체 일정에 **버퍼 20~30%** — 특히 마지막 주는 폴리싱·버그·배포 전용
- **"AI 작업 단위"의 완료 기준(Definition of Done)**
  - Play 모드에서 동작 확인 → 콘솔 에러 없음 → 커밋 완료

### 6-3. 예시 일정 (8주 프로젝트)

| 주차 | 마일스톤 | 산출물 |
|---|---|---|
| 1 | 기획 확정 | 코어 루프 한 줄, Must/Should/Could 목록, 레퍼런스 게임 |
| 2 | 프로토타입 | 회색 박스(graybox)로 코어 루프 동작 |
| 3 | **MVP** | Must 기능 전부 동작하는 빌드 |
| 4 | 플레이테스트 1 | 다른 팀 피드백 수집 → 우선순위 재조정 |
| 5 | 콘텐츠 확장 | Should 기능, 레벨/적 추가 |
| 6 | 아트·사운드 적용 | 게임 필 폴리싱 |
| 7 | 플레이테스트 2 + 버그 수정 | **기능 추가 동결(Feature Freeze)** |
| 8 | 빌드·배포 | itch.io 공개, 발표 |

### 6-4. 도구
- **GitHub Projects / Issues**: 칸반(To Do / In Progress / Done), 이슈 하나 = AI에게 줄 작업 하나
- (선택) Notion 등 팀이 익숙한 도구
- AI로 계획 돕기: "이 기획서를 Must/Should/Could로 나누고 8주 일정 초안을 짜줘" → **반드시 사람이 수정**

### 6-5. 워크시트 실습 (10분)
- 각자/팀별로: 코어 루프 한 줄 + Must 기능 5개 이하 + 3주 뒤 MVP 정의 작성
- 2~3팀 발표 → 범위가 너무 큰 경우 즉석에서 줄이기 시연

## 7. 워크플로우: GitHub Desktop으로 버전관리 (25분)

**목표**: AI가 코드를 대량으로 바꾸는 환경에서 **"언제든 되돌릴 수 있다"** 는 안전장치를 갖추기.

### 7-1. 왜 버전관리인가 (AI 관점에서 설명)
- AI는 한 번에 여러 파일을 바꾼다 → 잘못되면 어디가 바뀌었는지 모름
- **규칙: AI에게 작업을 시키기 전에 커밋, 결과가 좋으면 또 커밋**
- 팀 협업: 같은 프로젝트를 여러 명이 수정

### 7-2. 핵심 개념 (최소한만)
- Repository / Commit / Push / Pull / Branch / Merge
- 비유: 커밋 = 게임 세이브 포인트, 브랜치 = 평행 세계

### 7-3. 실습 순서
1. GitHub 계정 생성(각자 진행), GitHub Desktop 설치·로그인
2. 저장소 생성 시 **.gitignore 템플릿을 Unity로 선택** (Library/, Temp/ 등 제외)
3. Unity 프로젝트를 저장소 폴더에 생성 (8번과 연결)
4. 변경 확인 → 커밋 메시지 작성 → Push
5. 다른 컴퓨터(또는 팀원)에서 Clone → Pull
6. 브랜치 만들어서 실험 → 실패 시 **Discard changes / 이전 커밋으로 되돌리기** 시연

### 7-4. Unity 협업 주의사항
- Project Settings에서 **Asset Serialization = Force Text**, **Visible Meta Files** 확인
- `.meta` 파일은 반드시 함께 커밋
- **씬(.unity) 파일은 동시에 수정하면 충돌이 잦다** → 씬 담당자 정하기, 프리팹 단위로 작업 분리
- 큰 바이너리 에셋(음원·영상·대형 텍스처)은 **Git LFS** 고려
- 커밋 메시지 규칙 예: `[기능] 플레이어 점프 추가`, `[수정] 적 충돌 버그`

## 8. Unity 프로젝트 생성 & 게임 실행 (30분)

**목표**: 모든 수강생이 **자기 컴퓨터에서 프로젝트를 만들고 Play 버튼으로 실행**하는 단계까지 도달. (이 체크포인트를 통과해야 9번 진행)

### 8-1. 설치
- Unity Hub 설치 → Unity 6 LTS 버전 설치 (빌드 모듈: Windows / WebGL, Mac 사용자는 Mac 모듈)
- 코드 에디터: Visual Studio 또는 VS Code / Rider
- ⚠️ 설치 용량·시간이 크므로 **수업 전 사전 설치 공지** 필수

### 8-2. 프로젝트 생성
- 템플릿: Universal 2D 또는 Universal 3D (URP)
- 저장 위치: 7번에서 만든 GitHub 저장소 폴더

### 8-3. 에디터 투어 (반드시 이해해야 할 6가지)
| 창 | 역할 | 비유 |
|---|---|---|
| Scene | 게임 세계를 편집하는 작업대 | 무대 |
| Game | 플레이어가 보는 화면 | 객석 |
| Hierarchy | 씬 안의 오브젝트 목록 | 출연진 명단 |
| Inspector | 선택한 오브젝트의 컴포넌트·설정값 | 배우 프로필 |
| Project | 에셋 파일 전체 | 창고 |
| Console | 로그·에러 메시지 | 무전기 |

- 핵심 개념: **GameObject = 컴포넌트를 담는 그릇**, 스크립트도 컴포넌트다
- **Play 모드 중 변경 사항은 종료 시 사라진다** (초보자가 가장 많이 겪는 실수)

### 8-4. 미니 실습
1. 큐브(또는 스프라이트) 하나 배치
2. AI(채팅)에게 "WASD로 움직이는 Unity C# 스크립트" 요청 → 직접 파일 생성·붙여넣기·컴포넌트 부착
3. Play → 움직이는지 확인 → 일부러 오타 내고 Console 에러 읽기
4. Build Profiles에서 빌드 → 실행 파일로 실행
5. GitHub Desktop으로 커밋·푸시

> **체크포인트**: "AI가 준 코드를 내가 직접 붙여 넣어 움직이게 만들 수 있다" — 이 수동 과정을 겪어봐야 9번에서 AI가 자동으로 하는 일이 무엇인지 이해할 수 있다.

## 9. 에디터에 MCP 연결해서 개발 (40분)

**목표**: AI가 채팅창 밖으로 나와 **Unity 에디터를 직접 조작**하는 개발 방식을 체험.

### 9-1. 2번 복습: 이제 직접 연결한다 (5분)
- 2-5의 구조 그림 다시 띄우기: AI 클라이언트 ↔ MCP 서버 ↔ Unity 에디터 패키지
- 8번과 비교:
  - **8번(수동)**: AI가 코드 출력 → 사람이 복사·붙여넣기·부착·실행·에러 복사
  - **MCP**: AI가 직접 스크립트 생성, 오브젝트 배치, 컴포넌트 부착, 콘솔 에러 읽기, 수정까지 수행

### 9-2. 설치·연결 실습 (10분)
- 배포한 설치 가이드 1장([MCP설치가이드.md](MCP설치가이드.md))을 따라 다 같이 진행
  1. Unity CLI 설치 → 프로젝트에 연결용 패키지 설치(`unity pipeline install`)
  2. AI 클라이언트에 MCP 서버 등록(`unity mcp configure claude-code`)
  3. 연결 상태 확인 → AI에게 "현재 씬의 Hierarchy를 알려줘" → 응답이 오면 성공
- ⚠️ 패키지 이름·설치 방법·지원 버전이 빠르게 바뀌므로 **수업 직전 버전으로 설치 가이드를 1장으로 따로 배포**
- 자주 막히는 지점 미리 안내: Unity 에디터가 꺼져 있음, 다른 프로젝트가 열려 있음, 방화벽/포트, Node·Python 등 런타임 미설치

### 9-3. 라이브 데모 (10분)
3번에서 만든 게임과 같은 장르를 **MCP로 다시** 만들어 비교
1. "플레이어 오브젝트를 만들고 이동 스크립트를 붙여줘"
2. "적 스폰 시스템 추가해줘" → Play → "콘솔 에러 확인하고 고쳐줘"
3. "UI에 점수 표시해줘"
- 매 단계마다 GitHub Desktop에서 **변경된 파일 목록을 보여주며** "AI가 무엇을 바꿨는지" 확인

### 9-4. 수강생 실습 (15분)
- 8번에서 만든 자기 프로젝트에 MCP 연결
- 과제: 6번에서 정한 **Must 기능 중 1개**를 MCP로 구현 → Play 확인 → 커밋

### 9-5. MCP 사용 안전 수칙
- **작업 전 커밋** (7번 규칙 재강조)
- 한 번에 하나의 기능만 요청 (작은 단위)
- AI가 바꾼 씬/스크립트를 **반드시 Play로 직접 검증**
- 이해 못 한 코드는 "이 코드가 뭘 하는지 설명해줘"로 확인 후 커밋
- 자동 실행 권한은 신중하게: 파일 삭제·대량 변경 요청은 승인 후 진행

## 부록 B. 예상 질문 & 답변 포인트
- **"AI가 다 해주면 코딩 공부는 필요 없나요?"** → AI 결과를 검증하고 방향을 정하려면 기본 개념은 필수. 오늘 8번을 수동으로 한 이유.
- **"AI로 만든 게임 팔아도 되나요?"** → 플랫폼별 AI 콘텐츠 정책과 에셋 라이선스 확인 필요. 코드보다 에셋에서 문제가 생기기 쉬움.
- **"Mac 사용자인데 Windows 빌드 되나요?"** → 가능한 경우가 많지만 백엔드·모듈 설정에 따라 다름. 반대로 Mac 배포용 서명·공증은 Mac 환경이 필요.
- **"콘솔 출시 가능할까요?"** → 개인 학생이 바로 하기는 어렵다. PC로 먼저 성과를 내고 퍼블리셔·인디 프로그램을 통한 경로가 현실적.
